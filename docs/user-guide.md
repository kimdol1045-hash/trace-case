# TC 테스트 관리 도구 사용 가이드

이 문서는 현재 구현된 TC 웹 화면을 기준으로 테스트 자산 작성, QA 사이클 실행, 내부 이슈 추적, Slack 요청과 지식 조회까지의 전체 사용 방법을 설명한다.

## 1. 기본 운영 원칙

- 하나의 팀이 하나의 워크스페이스를 함께 사용한다.
- 로그인과 역할 구분은 없다. 접속한 팀원 누구나 테스트케이스와 이슈를 만들고 사이클을 실행할 수 있다.
- Jira와 Google Drive는 연결하지 않는다. 이슈는 TC 내부에서 관리하고 첨부파일은 private Cloudflare R2에 저장한다.
- 로컬 개발 환경의 첨부 저장소는 R2와 같은 S3 API를 사용하는 MinIO다.
- 테스트케이스는 기본적으로 사람이 수동 작성한다. Slack 기반 자동 생성은 별도 생성 API가 연결된 이후 사용하는 확장 기능이다.

## 2. 메뉴 구성

| 메뉴 | 용도 |
|---|---|
| `Overview` | 진행 중인 QA와 위험 신호를 그래프와 요약 지표로 확인 |
| `Test Library` | 카테고리, 상위일감, 테스트케이스 작성과 정리 |
| `Cycles` | 상위일감 또는 라벨 범위로 테스트 사이클 생성과 실행 |
| `Issues` | 실행 중 발견한 결함과 일반 내부 이슈 관리 |
| `Reports` | 사이클 결과와 품질 지표를 필터별로 상세 분석 |
| `Slack Work Items` | Slack에서 수집한 일감 원문, thread, 수정 이력 확인 |
| `자동 생성 실패` | 최종 실패한 자동 생성 작업과 봉인된 시도 이력 확인, 허용된 조건부 재시도 |
| `품질 후보 검토` | 안전 projection으로 만든 자동 생성 품질 후보의 두 사람 검토 원장 관리 |
| `Knowledge` | Slack 결정사항과 테스트 히스토리에서 구축한 QA 지식 조회 |
| `Integrations` | Slack과 첨부파일 저장소의 실제 연결 상태 확인 |

## 3. 가장 빠른 QA 진행 순서

1. `Test Library`에서 카테고리를 만든다.
2. 카테고리에 상위일감을 만든다.
3. 상위일감 아래에 테스트케이스를 작성한다.
4. `Cycles`에서 상위일감 하나 또는 라벨 여러 개를 실행 대상으로 선택한다.
5. 사이클을 만든 뒤 `사이클 시작`을 누른다.
6. 실행 화면에서 테스트케이스와 스텝을 선택하고 WEB, AOS, iOS별 결과를 저장한다.
7. 결함이 발견되면 실행 화면에서 `이슈 생성`을 눌러 현재 실행에 자동 연결한다.
8. 필요한 실행이 끝나면 사이클 상세에서 `사이클 완료`를 누른다.
9. `Overview`에서 현재 위험을 보고 `Reports`에서 상세 결과를 분석한다.

## 4. Test Library 사용법

### 4.1 카테고리 관리

카테고리는 테스트 영역을 구분하는 최상위 단위다.

1. `Test Library` 왼쪽의 `테스트 카테고리` 제목 옆 `+`를 누른다.
2. 카테고리명을 입력하고 `생성`을 누른다.
3. 카테고리를 클릭하면 오른쪽 목록이 해당 카테고리의 상위일감과 케이스로 전환된다.
4. 카테고리 행의 이름을 수정하거나 삭제 버튼으로 삭제할 수 있다.

카테고리 숫자는 해당 카테고리에 속한 테스트케이스 수다. 검색과 필터를 사용해도 원본 카테고리 수가 임의로 0으로 바뀌지 않아야 한다.

### 4.2 상위일감 만들기

상위일감은 여러 테스트케이스를 묶는 Jira 상위 작업과 같은 단위다.

1. 상단의 `+ 상위일감 만들기`를 누른다.
2. 카테고리, 키, 서머리를 입력한다.
3. 필요하면 설명, 담당자, 라벨을 입력한다.
4. 저장 버튼을 눌러 생성한다.

모달을 닫거나 취소하면 생성되지 않는다. 상위일감 제목을 클릭하면 상세 화면에서 설명, 카테고리, 담당자와 라벨을 수정할 수 있다. 하위 테스트케이스를 다른 상위일감으로 모두 옮겨도 비어 있는 기존 상위일감은 그대로 유지된다.

### 4.3 테스트케이스 검색과 필터

- 검색: 케이스 키, 서머리, 상위일감, 담당자, 라벨
- 우선순위: Highest, High, Medium, Low
- 라벨: 입력한 라벨을 포함하는 케이스
- `삭제 항목 포함`: 삭제된 케이스까지 함께 조회
- `필터 초기화`: 검색 조건을 모두 해제

목록이 길면 하단의 `다음 50개 불러오기`로 이어서 조회한다.

### 4.4 테스트케이스 이동과 순서 변경

- 테스트케이스의 드래그 핸들을 잡고 같은 상위일감 안의 다른 케이스 위치에 놓으면 순서가 바뀐다.
- 다른 상위일감 영역에 놓으면 해당 상위일감으로 이동한다.
- 다른 카테고리에 속한 상위일감으로 이동하면 케이스의 카테고리도 대상 상위일감에 맞춰 변경된다.
- 이동 대상이 비어 있어도 상위일감 영역에 놓을 수 있다.

케이스 행을 한 번 클릭하면 상세 화면으로 이동한다. 행의 슬라이드 또는 보조 메뉴에서는 복사, 삭제, 복원을 사용할 수 있다.

## 5. 테스트케이스 작성과 수정

### 5.1 새 테스트케이스 작성

1. `Test Library` 상단의 `+ 테스트케이스 만들기`를 누른다.
2. 서머리에 검증 목적을 한 문장으로 입력한다.
3. 오른쪽 `세부 정보`에서 카테고리와 상위일감을 선택한다.
4. 우선순위, 담당자, 라벨을 입력한다. 라벨 여러 개는 쉼표로 구분한다.
5. 각 스텝에 `사전조건 → 테스트 동작 → 기대 결과`를 입력한다.
6. 필요하면 `+ 스텝 추가`로 스텝을 늘린다.
7. `테스트케이스 저장`을 누른다.

각 스텝의 사전조건, 테스트 동작, 기대 결과는 모두 필수다. 생성 화면에 진입하거나 입력만 한 상태에서는 케이스가 만들어지지 않으며 저장 버튼을 눌러 검증을 통과한 경우에만 생성된다.

### 5.2 테스트케이스 상세

상세 화면에서 다음 항목을 수정할 수 있다.

- 서머리
- 설명
- 스텝별 사전조건, 테스트 동작, 기대 결과
- 스텝 순서와 스텝 추가·삭제
- 카테고리, 우선순위, 담당자, 라벨

수정 후에는 반드시 `변경사항 저장`을 누른다. 저장할 때 새 버전과 수정 시각이 기록된다.

### 5.3 변경 이력과 복원

`변경 이력` 탭에서는 버전별로 바뀐 필드, 변경 전 값, 변경 후 값과 시각을 확인한다. 과거 버전의 `복원`을 누르면 과거 내용을 현재 버전에 덮어쓰는 대신 복원 내용을 가진 새 버전이 생성된다.

### 5.4 삭제와 복원

- 상세 화면의 `삭제`는 확인 단계를 거친다.
- 목록에서는 삭제 항목 포함 필터를 사용해 삭제된 케이스를 다시 찾을 수 있다.
- 삭제된 케이스는 `삭제 복원`으로 되돌릴 수 있다.

## 6. 테스트 사이클 사용법

### 6.1 사이클 상태

| 상태 | 의미 | 결과 입력 |
|---|---|---|
| `미진행` (`PLANNED`) | 실행 범위를 만들었지만 시작하지 않음 | 불가 |
| `진행 중` (`IN_PROGRESS`) | 실제 QA 수행 중 | 가능 |
| `완료` (`COMPLETED`) | 실행이 종료되고 결과가 잠김 | 불가 |

사이클 목록 상단의 상태 카드를 누르면 해당 상태만 조회한다. 같은 카드를 다시 누르거나 `All`을 누르면 전체 목록으로 돌아간다.

### 6.2 새 사이클 만들기

1. `Cycles`에서 `+ 새 테스트 사이클`을 누른다.
2. 사이클명, 시작일, 설명을 입력한다.
3. 실행 대상 형식을 선택한다.
   - `상위 일감`: 상위일감 하나를 선택한다.
   - `라벨`: 라벨을 여러 개 선택할 수 있으며 케이스 중복은 제거된다.
4. 선택 모달에서 카테고리를 펼치고 검색해 상위일감을 고른다. 상위일감은 해당 사이클 범위에 사용할 단위다.
5. 라벨 선택 모달에서는 각 라벨에 포함된 테스트케이스를 펼쳐 확인한다.
6. 오른쪽 미리보기의 포함 케이스 수와 목록을 확인한다.
7. `사이클 만들기`를 누른다.

사이클 생성 시 포함된 테스트케이스 버전이 pinned snapshot으로 고정된다. 이후 라이브러리 원본을 수정해도 이미 생성된 사이클의 실행 내용은 자동으로 바뀌지 않는다.

### 6.3 사이클 상세

사이클 상세에서는 실행 대상, 포함 케이스, 플랫폼 결과, 위험 결과와 진행률을 확인한다.

- 사이클명과 설명은 완료 전 수정할 수 있다.
- 포함된 테스트케이스를 클릭하면 라이브러리 원본 상세로 이동한다.
- pinned 버전과 현재 최신 버전 번호는 케이스 행의 메타정보에서 확인한다.
- 별도 `Latest diff` 버튼은 제공하지 않는다.
- 미진행 사이클만 삭제할 수 있다.
- `사이클 시작`을 누르면 실행 범위가 잠기고 실행 화면으로 이동한다.

### 6.4 사이클 실행

1. 왼쪽에서 실행할 테스트케이스를 선택한다.
2. 가운데 표에서 테스트 스텝을 선택한다.
3. 상단 실행결과에서 WEB, AOS, iOS 중 실행할 플랫폼을 선택한다.
4. 드롭다운에서 `PASS`, `FAIL`, `BLOCKED` 또는 `UNEXECUTED`를 선택한다.
5. 필요한 비고를 입력한다.
6. 선택한 플랫폼과 스텝의 결과 저장 버튼을 누른다.
7. 다음 스텝과 플랫폼도 같은 방법으로 저장한다.

결과는 테스트케이스 전체가 아니라 스텝별·플랫폼별로 저장된다. 하나의 테스트케이스에 스텝이 여러 개 있으면 각 스텝을 각각 선택해 결과를 남긴다.

### 6.5 실행결과 의미와 통합결과

| 결과 | 의미 |
|---|---|
| `UNEXECUTED` | 해당 플랫폼 또는 스텝을 실행하지 않음 |
| `PASS` | 기대 결과와 일치 |
| `FAIL` | 기대 결과와 불일치 |
| `BLOCKED` | 환경이나 선행 조건 때문에 실행할 수 없음 |

통합결과는 WEB, AOS, iOS 중 실제 판정 가능한 값만 집계한다.

- `UNEXECUTED`는 집계에서 제외한다.
- `BLOCKED`도 통합결과에서 제외한다.
- 집계 대상 중 하나라도 `FAIL`이면 통합결과는 `FAIL`이다.
- 집계 대상이 모두 `PASS`이면 통합결과는 `PASS`다.
- 집계할 값이 없으면 `UNEXECUTED`다.

따라서 세 플랫폼을 반드시 모두 실행할 필요는 없다. 예를 들어 WEB만 `PASS`이고 AOS와 iOS가 `UNEXECUTED`이면 통합결과는 `PASS`다.

### 6.6 실행 중 이슈 생성

실행결과와 관계없이 현재 선택한 스텝에서 이슈를 만들 수 있다.

1. `이슈 생성`을 누른다.
2. 모달에 자동 입력된 서머리, 사전조건, 재현 스텝, 기대 결과와 실제 결과를 확인한다.
3. 심각도를 선택하고 내용을 수정한다.
4. 필요하면 로컬 파일을 선택하거나 끌어놓는다.
5. `이슈 생성`을 누른다.

생성한 이슈는 현재 실행 시도에 자동 연결된다. 같은 실행에서 이슈를 여러 개 만들 수 있다.

### 6.7 사이클 완료와 다시 열기

- 진행 중 사이클의 필요한 실행을 마치고 상세 화면에서 `사이클 완료`를 누른다.
- 미실행 항목이 있으면 경고를 확인한 뒤 미실행 포함 완료를 선택할 수 있다.
- 완료된 사이클은 읽기 전용이다.
- 추가 실행이 필요하면 `다시 열기`로 진행 중 상태로 되돌린다.

## 7. Issues 사용법

### 7.1 이슈 목록과 상태 필터

상단 카드에서 `열림`, `진행 중`, `해결됨`, `종료` 상태를 선택한다. 카드 숫자는 현재 선택한 상태와 무관한 전체 상태별 건수이며, 예를 들어 종료 필터를 선택해도 열림 건수는 유지된다.

추가 필터는 다음과 같다.

- 사이클
- 상태
- 심각도
- 키, 서머리, 담당자 검색

이슈 상태는 `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`, `REOPENED`를 사용한다.

### 7.2 일반 이슈 만들기

1. `Issues`에서 `+ 이슈 만들기`를 누른다.
2. 서머리, 사전 조건, 재현 스텝, 기대 결과, 실제 결과를 입력한다.
3. 심각도와 담당자를 설정한다.
4. `관련 테스트케이스`에서 사이클을 선택하고 해당 사이클 안의 케이스를 연결한다. 연결은 선택 사항이다.
5. 첨부파일을 선택하거나 끌어놓는다.
6. 저장 버튼으로 생성한다.

재현 스텝은 하나의 입력 영역으로 작성한다. 이슈 생성 화면에 진입하거나 초안만 작성한 상태에서는 이슈가 생성되지 않는다.

### 7.3 이슈 상세와 수정

이슈 상세 화면은 생성 화면과 같은 구조로 내용을 수정할 수 있다. 연결된 사이클과 테스트케이스, 첨부파일, 댓글과 변경 이력을 함께 확인한다. 변경 이력에는 바뀐 항목과 이전·이후 값이 표시된다.

이슈 삭제는 화면에서 `삭제`로 표시되지만 데이터 추적을 위해 내부적으로 soft delete와 감사 로그를 남긴다.

## 8. 첨부파일 사용법

첨부파일은 이슈 생성·상세와 사이클 실행의 이슈 생성 모달에서 추가한다.

- 여러 파일을 한 번에 선택할 수 있다.
- 파일당 최대 크기는 기본 50MB다.
- 이미지: PNG, JPEG, GIF, WebP
- 영상: MP4, WebM
- 문서·로그: TXT, CSV, JSON, PDF, ZIP, GZIP

업로드 흐름은 다음과 같다.

1. 브라우저가 파일의 SHA-256을 계산한다.
2. 서버가 짧은 수명의 업로드 URL을 발급한다.
3. 브라우저가 파일을 private R2 bucket으로 직접 업로드한다.
4. 서버가 크기, MIME type, checksum을 검증한 뒤 첨부 레코드를 확정한다.

R2 bucket은 공개되지 않는다. 다운로드는 TC 서버를 통해 수행하고 access key는 브라우저에 노출하지 않는다. 보존 기간은 제한하지 않지만 사용자가 삭제하면 soft delete 이력과 감사 로그를 남긴 뒤 저장 객체도 삭제한다.

## 9. Overview와 Reports

### 9.1 Overview

Overview는 현재 확인이 필요한 내용을 빠르게 보는 운영 대시보드다.

- 사이클 상태 분포
- 테스트 실행 결과와 실패 추이
- 열린 이슈와 심각도
- 상위일감별 위험
- 즉시 확인할 BLOCKED 또는 실패 신호

Overview에서는 데이터를 편집하지 않고, 각 카드나 표를 통해 상세 메뉴로 이동한다.

### 9.2 Reports

Reports는 대시보드보다 상세한 분석 화면이다.

- 사이클별 결과
- 상위일감과 라벨별 품질
- 플랫폼별 결과
- 이슈 심각도와 상태
- 기간·범위별 상세 데이터

즉, Overview는 현재 상황과 위험을 빠르게 파악하는 화면이고 Reports는 원인을 분석하거나 결과를 공유하는 화면이다.

## 10. Slack Work Items와 Knowledge

### 10.1 Slack Work Items

Slack 연동이 설정되면 allowlist 채널의 일감 메시지와 thread를 자동 수집한다.

- 목록에서 채널과 처리 상태를 검색한다.
- 상세에서 root 메시지, 답글, 수정·삭제 revision을 시간순으로 확인한다.
- `대화 다시 동기화`로 Slack thread의 최신 내용을 다시 수집한다.
- 원문이 Slack에서 수정되거나 삭제돼도 이미 수집한 revision은 근거 이력으로 남는다.

### 10.2 Knowledge

Knowledge는 Slack 결정, 요구사항, 테스트케이스, 실행과 이슈 히스토리를 연결한 QA 지식 화면이다.

- 키워드 또는 의미 기반으로 지식을 검색한다.
- `ACTIVE`, `AMBIGUOUS`, `SUPERSEDED`, `RETRACTED` 상태를 확인한다.
- 지식의 원본 Slack 메시지나 테스트 자산 근거를 확인한다.
- 자동 테스트케이스 생성 API는 이후 이 지식과 기존 테스트 히스토리를 참조한다.

`AMBIGUOUS`, `SUPERSEDED`, `RETRACTED` 지식은 현재 확정된 생성 근거로 사용하지 않는다.

### 10.3 자동 생성 실패와 품질 후보 검토

`자동 생성 실패`는 최종 실패한 생성 작업의 원인, 생성·공급자·전달 시도와 append-only 이벤트를 확인하는 운영 화면이다. 재시도가 허용된 실패만 조건을 추가해 다시 실행할 수 있으며 공급자의 원문 응답이나 secret은 표시하지 않는다.

`품질 후보 검토`는 별도의 release 승인 화면이 아니다. 화면 상단의 `CANDIDATE / UNREVIEWED` 또는 `CANDIDATE / REVIEWED_NOT_RELEASE_CERTIFIED` 경계를 항상 확인한다.

1. 검토 진행 상태, 16개 분류, 물질화 상태 또는 안전 후보 별칭으로 서버 목록을 필터한다.
2. 후보를 직접 선택한다. 첫 항목은 자동 선택되지 않는다.
3. root/case/step/evidence 수량, 캡처 bucket과 revision, 정확한 fingerprint, privacy scan, 분류·중복·물질화 증명과 append-only 결정 원장을 확인한다.
4. 검토자 token을 현재 화면의 token panel에 입력한다. token은 React 메모리에만 유지되고 `localStorage`나 `sessionStorage`에는 저장되지 않는다.
5. 승인 또는 거절을 누르고 확인 dialog에서 snapshot fingerprint를 다시 확인한다. 거절은 고정 사유 코드를 선택해야 한다.
6. 첫 번째 승인 뒤에는 `1/2`가 표시된다. 같은 검토자는 두 번째 슬롯을 채울 수 없으며 서로 다른 검토자의 token으로 두 번째 승인을 남겨야 `2/2`가 된다.

거절은 terminal 상태다. 인증이 만료되면 token을 다시 입력하고, stale `409`가 발생하면 화면이 새 후보 상태를 불러온 뒤 fingerprint를 다시 확인한다. 두 명의 승인이 끝나도 credentialed provider live gate와 실제 sample 검증이 별도로 끝나기 전에는 release 인증이 아니다.

## 11. Integrations 확인

`Integrations`에서는 다음 상태를 확인한다.

- Slack 수집 방식과 credential 설정 상태
- 수집 허용 채널 allowlist
- 최근 이벤트와 retry·실패 작업
- 첨부 저장소 provider, bucket, 파일 크기 제한과 준비 상태

첨부 저장소가 `READY`가 아니면 운영 환경의 R2 endpoint, bucket, access key, secret, CORS 설정을 확인한다. 로컬에서는 `MINIO · tc-attachments`가 `READY`로 표시되는 것이 정상이다.

## 12. 화면 이동 규칙

- 목록에서 항목을 클릭하면 상세 화면으로 이동한다.
- 생성 성공 후에는 생성된 상세 화면으로 이동하며 브라우저 뒤로가기로 미저장 생성 화면을 되살리지 않는다.
- 생성 화면의 취소는 목록으로 돌아가며 초안을 저장하지 않는다.
- 상세 화면의 `목록으로` 또는 뒤로가기 버튼은 해당 메뉴 목록으로 이동한다.
- 페이지 이동 중 이전 화면의 데이터가 새 화면에 잠깐 노출되지 않도록 route별 데이터를 분리한다.

## 13. 오류와 충돌이 표시될 때

- `다시 시도`: 일시적인 조회 실패일 때 사용한다.
- `API 다시 연결`: 실제 API가 일시적으로 중단됐을 때만 표시된다.
- 충돌 메시지: 다른 변경이 먼저 저장된 경우다. 새로고침한 뒤 최신 내용을 기준으로 다시 수정한다.
- 첨부 업로드 부분 실패: 이슈가 먼저 생성됐을 수 있다. 메시지에 표시된 이슈 상세로 이동해 파일만 다시 첨부한다.
- 저장 버튼이 비활성화됨: 필수값, 사이클 상태, 삭제 상태 또는 진행 중인 저장 요청을 확인한다.

## 14. 로컬 실행 방법

최초 한 번 Node.js 22+, pnpm 10+, Python 3.12+, Docker를 준비한다.

```bash
python3 -m venv .venv
pnpm run setup
```

전체 개발 환경을 실행한다.

```bash
pnpm dev
```

- Web: <http://localhost:5173>
- API health: <http://localhost:8000/api/health>
- OpenAPI: <http://localhost:8000/docs>
- MinIO API: <http://127.0.0.1:59000>
- MinIO console: <http://127.0.0.1:59001>

개발 프로세스는 `Ctrl-C`로 종료한다. 컨테이너만 내리려면 다음 명령을 사용한다.

```bash
pnpm infra:down
```

## 15. 운영 전 체크리스트

- [ ] 팀 내부망 또는 VPN에서만 웹과 API에 접근 가능하다.
- [ ] 카테고리, 상위일감, 테스트케이스 생성·수정·삭제·복원이 동작한다.
- [ ] 사이클 시작 전 결과 입력이 막히고 시작 후에만 활성화된다.
- [ ] WEB, AOS, iOS별 스텝 결과가 각각 저장된다.
- [ ] FAIL 또는 BLOCKED 비고가 실행 이력에 남는다.
- [ ] 실행 중 만든 이슈가 현재 실행 시도에 자동 연결된다.
- [ ] 이슈 상태 필터를 변경해도 다른 상태 카드 건수가 유지된다.
- [ ] R2 bucket이 private이고 direct upload CORS가 설정되어 있다.
- [ ] 첨부 업로드, 다운로드, 삭제를 실제 파일로 확인했다.
- [ ] Slack allowlist 외 채널이 수집되지 않는다.
- [ ] PostgreSQL과 R2의 백업·복구 절차가 준비되어 있다.
